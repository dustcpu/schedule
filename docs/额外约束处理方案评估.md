# 额外约束（特殊要求）处理方案评估

> 2026-10-03 撰写。目的是回答一个具体问题：**「特殊要求」这一环要不要引入大模型，
> 引入后放在哪里、代价是什么、有没有更省的路。**
> 本文只做技术评估，不含任何讨论过程。

---

## 1. 问题是什么

界面上有一个自由文本框「② 特殊要求」，教务老师可以把排课时的额外要求写进去。
但引擎**不是**自然语言理解系统，它按固定格式逐行解析。结果是：

- 写法稍有偏差 → 整条要求被忽略；
- 想支持一种新的要求 → 必须在引擎里预先写死代码；
- 老师必须被"培训"成按格式填，否则填了等于没填。

这个矛盾的本质是：**入口是自由的（自然语言），出口是严格的（结构化）**，
中间那段适配现在靠一条正则硬撑。

---

## 2. 现状盘点：约束是从哪里进来的

引擎目前有 **4 个**约束入口，能力边界差别很大：

| # | 入口 | 载体 | 能表达什么 | 谁来填 |
|---|---|---|---|---|
| A | **课时标准** | `input.xlsx` 的 sheet | 每科的选考/非选考周课时、连堂节数、连堂日 | 教务 |
| B | **排课设置** | 外壳写出的 `hard_limits.json` | 作息（节数/时长/课间）、固定课（班会/研究性学习/校本课）、班级设置、连堂规则（学科/指定日）、求解参数 | 软件界面开关 |
| C | **特殊要求** | `requirements.txt`（自由文本） | **只有一种**：指定某位教师教某个班的某个学科 | 教务 |
| D | **额外硬约束** | `hard_limits.json` 的 `extra_constraints` | 与 C 同源，实际拼进 `requirements.txt` 一起解析 | 软件界面 |

**结论：A、B 两个入口是"表单"，能力被写死但可靠；C、D 是"自由文本"，只支持 1 种语义。**
所谓"加一条额外约束要改代码"，说的就是 C/D 这条路。

### 2.1 特殊要求现在能识别什么

解析器在 `engine/scheduler/data/load.py` 的 `_parse_teacher_constraints()`，
支持三种等价写法（`T001=C01语文` / `T001教C01语文` / `张老师教高二1班语文`），
并且：

- 会剥掉行首的 `1.` `1、` `(1)` `①` `- ` 等列表编号；
- 容忍 `T030 ↔ T30`、`C01 ↔ C1` 这类补零/去零差异（只在唯一匹配时接受）；
- 学科名做归一化（`信息课/计算机 → 信息`、`心理健康 → 心理` 等）；
- **解析不了的行不再静默丢弃**，而是分两类回传 `status.json` 的 `warnings`：
  - "像是教师指定但语法无法解析" → 附具体原因（哪个 ID 不在表里、表里近似的写法是什么）；
  - "该类要求当前不支持" → 附当前支持的格式示例。
- 前端选完输入文件即做预检，把这类提示提前显示出来。

也就是说：**"宽容度"和"可解释性"已经做得不错了，缺的是"理解力"和"覆盖面"。**

---

## 3. 把问题拆成三层

一条要求从"老师说的话"到"出现在课表里"，要过三道关：

| 层 | 干什么 | 现状 |
|---|---|---|
| **L1 语言层** | 把中文变成结构化数据 | 只有一条正则，只认"教师指定" |
| **L2 能力层** | 这条约束引擎能不能表达？ | **真正的瓶颈**（见下） |
| **L3 求解层** | 加进去之后还能不能按时排出解 | 已知：25 班约 3 分钟，时间已顶格 |

**关键判断：L2 才是现在卡住的地方。** 大模型能完美解决 L1，但如果 L2 里没有对应的
变量和约束，结构化数据再漂亮也只是"翻译正确但无处安放"。

举两个真实的例子说明这个区分：

| 要求 | 卡在哪一层 |
|---|---|
| `T30教C05数学` | **都不卡**——L1 已有正则，L2 已有语义（把 (班级, 学科) 的任课教师收缩为 1 人并锁定） |
| `T30 不能上周二的课` | **卡在 L2**——引擎里没有"教师 × 星期"的禁排变量 |
| `T30 所带的班里必须有一个是 C05` | **卡在 L2**——这是教师—班级的存在性/基数约束，需要引入"教师是否带某班"的布尔变量 |
| `非物理选科班每周加一节物理` | **不卡**——本质是改课时，用「课时标准」的非选考周课时就能表达，只是现在没有"按班型设课时"的语法 |

---

## 4. 需求分类：A / B / C 三类

把可能遇到的要求按"改造量"分三类，这是后面所有决策的基础。

### A 类：现在就支持（不用动代码）

- 指定某位教师教某个班某个学科（`T30教C05数学`）
- 作息、固定课、连堂学科与指定日、周课时（走 `hard_limits.json` 与「课时标准」）
- 求解参数（时限、方案数、候选教师数——目前写在 `SolverConfig::default()`）

### B 类：模型能表达，但需要补建模（改造量中等）

| 需求 | 需要的改动 | 粗估 |
|---|---|---|
| 某教师某天不排课 / 某时段不可用 | 给 `x[班级, 学科, 天, 节]` 加禁排约束 | 小 |
| 某班某半天不排主科（如周五大扫除） | 同上，按班级屏蔽若干格 | 小 |
| 某学科不排第 1 节 / 不排下午 | 现成的软约束里已有类似结构，转成硬约束即可 | 小 |
| 某教师每周带班数上下限 | 需要"教师-班级-学科"分配变量（见 §7 的 `y` 变量） | 中 |
| 按班型设不同周课时（如"实验班数学 +1"） | 扩「课时标准」的表达：按班型覆盖课时 | 中 |
| 某两天之间某科不连排 | 加"间隔"约束 | 中 |

### C 类：需要新建模（改造量大，且影响求解性能）

| 需求 | 为什么难 |
|---|---|
| 某教师所带的班里必须包含某班（存在性/基数） | 需要"教师是否带某班"的布尔变量 + 基数约束，与现行的「教师预分配」机制冲突 |
| 教师带班数尽可能均匀（作为优化目标而非罚项） | 需要把教师分配纳入决策变量，从"预分配 + 微调"改成"联合求解" |
| 两位教师必须教同一年级 / 不能教同一年级 | 需要教师分组变量的组合约束 |
| "如果 A 则 B"这类条件约束 | 需要指示变量，模型规模上升，求解时间会明显变长 |

> **一个重要的结构性事实**：现在"谁教哪个班"是在加载阶段**预分配**好的，
> 求解器只决定"什么时间上什么课"。如果有一天把教师分配也变成 CP-SAT 的决策变量
> （`y[班级, 学科, 教师]`），那么上表 B 类里一大半、以及 C 类的前两条，
> **会自然变得可表达**——因为约束有地方挂了。这是比"接大模型"更根本的一件事。

## 5. 四种可选方案

### 方案 0：维持现状（正则 + 文档规范）

- **做法**：继续用固定格式，靠界面上的《书写规范》和解析失败提示来"训练"用户。
- **优点**：零成本、零风险、完全离线、行为确定。
- **缺点**：只覆盖 A 类；老师仍然要学语法；任何新增要求都要改引擎。
- **工作量**：0。**但它不是长久之计**——只是给下面几个方案争取时间。

### 方案 1：结构化输入（表单 / 下拉 / 规则词典），不接模型

- **做法**：
  1. 前端把自由文本框换成"约束编辑器"：选类型（下拉）→ 填参数（班级、学科、教师、星期）；
  2. 生成规范文本或 JSON，写进 `requirements.txt`；
  3. 自由文本作为"辅助入口"保留，命中词典的自动转成结构化，未命中的按现在的逻辑给提示。
- **优点**：离线、免费、行为完全确定；老师不需要背语法（选项就是语法）；能顺带把 B 类需求按"填空"的方式加进来。
- **缺点**：只能覆盖"预先设计好的类型"，真正的新表述仍然进不来；表单多了界面会变复杂。
- **工作量**：小到中（前端为主，引擎侧几乎不动）。
- **性价比**：**最高**。它解决的是"老师不会写"，而这恰恰是当前最大的抱怨来源。

### 方案 2：软件内接大模型（可选加 RAG）

- **做法**：前端把老师的话（+ 约束 schema + 少量示例）发给大模型，模型输出结构化 JSON，
  校验后转成引擎能吃的格式；失败就回落到方案 1 的规则路径。
  RAG 变体：先把"支持哪些约束、怎么写"做成小知识库，调用时先喂给模型。
- **优点**：能理解任意表述，理论上覆盖最广；新增约束类型只需扩 schema，不用改解析代码。
- **缺点（逐条都很硬）**：
  1. **隐私**：教师姓名、班级名称、学校信息属校方数据，发给公网 API 就是**数据外传**；
  2. **离网不可用**：学校机房/教务电脑常见无外网或禁外网，一旦依赖云 API，"能不能用"就变成了外部条件；
  3. **密钥无法保密**：桌面程序里内置的 API key 是可以被提取的（客户端程序没有真正的秘密）。要安全就必须让老师自备 key，或者自建一个中转服务（又多一套运维）；
  4. **幻觉**：模型可能编出不存在的约束、或把"不要排周二"理解成"周二少排"。必须 schema 校验 + 让用户确认后才生效；
  5. **成本**：单次调用的钱可以忽略（一次排课就几条到几十条约束，每条几百 token），真正的成本在 prompt 维护、失败兜底、key 管理和网络异常处理；
  6. **RAG 对这件事是过度设计**：schema 加几个例子总共也就几百 token，直接写进 prompt 比做检索更准、更简单。RAG 只在"回答老师'这个需求能不能做、怎么做'"这类开放问答时才有价值。

### 方案 3：软件外转换 + 导入接口（模型不进软件）

- **做法**：
  1. 软件提供一个**结构化约束的导入/粘贴入口**（JSON 或规范文本），带 schema 校验和回显确认；
  2. 转换这件事发生在软件之外：由教务把老师的要求收集起来，交给任意可用的 AI
     工具（或人工）转换，把结果贴回软件；
  3. 转换用的 prompt 模板与 schema 由团队提供，对外只有一个"模板文件"。
- **优点**：软件不联网、不加依赖、不收 key、不发数据；零调用成本；转换用的模型可以随时替换（今天用免费额度，明天换更强的）。
- **缺点**：**老师不能自助**——需要有人中转；一致性依赖那个中转的人；量大时是人力成本。
- **工作量**：小（软件侧只要导入入口 + 校验 + 回显）。
- **定位**：**内部试点的最佳形态**，同时也是语料收集器——中转过程中攒下来的
  "原话 → 结构化"配对，正是将来做规则词典或微调的原材料。

## 6. 对比矩阵

| 维度 | 方案 0 现状 | 方案 1 结构化输入 | 方案 2 软件内接模型 | 方案 3 软件外转换 |
|---|---|---|---|---|
| 覆盖需求 | 仅 A 类 | A + 设计好的 B 类 | A + B + 部分 C（受 schema 限制） | 同方案 2（转换在外部） |
| 老师能否自助 | 要学语法 | ✔ | ✔ | ✘（需中转） |
| 开发量 | 0 | 小-中 | 中-大 | 小 |
| 运行成本 | 0 | 0 | 调用费可忽略，维护成本不低 | 0（人力） |
| 隐私风险 | 无 | 无 | ⚠️ 高（需脱敏或自建中转） | 无（软件侧） |
| 离线可用 | ✔ | ✔ | ✘ | ✔ |
| 行为确定性 | 高 | 高 | 中（需校验 + 确认） | 中（同左） |
| 加新约束类型的成本 | 改解析代码 | 改前端 + 解析 | 扩 schema（+ 引擎建模） | 同方案 2 |
| 密钥管理 | 无 | 无 | 需要（且无法在客户端保密） | 无 |

**一句话总结：方案 2 的能力最强，但它同时引入联网、花钱、隐私、密钥四件麻烦事；
而这四件事里，**隐私和离网是学校场景下最难绕开的**。

## 7. 推荐路线

**顺序是 0 → 1 → 3 →（确有必要再）2，而不是一步到位上模型。**

### 第 0 步（前置，必须先做）：写一份《约束能力清单》

把约束按 §4 的 A/B/C 三类列清楚，并定一份 **JSON schema** 作为唯一的机器接口。
这份清单是所有方案的公共地基：没有它，模型输出的东西没地方落；有了它，
"要不要接模型"会退化成一个小决定——模型只是个"填表员"，填的正是这张表。

清单要拉上引擎同学一起定（B/C 类的改造量只有他们能估准）。

**schema 草案**（示例，字段名待定）：

```json
{
  "version": 1,
  "constraints": [
    { "type": "assign_teacher",       "class": "C05", "subject": "英语", "teacher": "T30" },
    { "type": "teacher_unavailable",  "teacher": "T30", "days": [2] },
    { "type": "teacher_unavailable",  "teacher": "T12", "days": [5], "periods": [7, 8] },
    { "type": "class_unavailable",    "class": "C01",  "day": 5, "periods": [7, 8] },
    { "type": "teacher_max_classes",  "teacher": "T30", "max": 2 },
    { "type": "subject_per_week",     "class_filter": { "not_selected": "物理" },
                                       "subject": "物理", "count": 1 }
  ]
}
```

配套要求：
- 每条约束带 `type`，**未知 type 一律拒绝**（而不是猜）；
- 每条约束单独校验，一条不合法只丢那一条，并把原因回传 warnings；
- 生效结果要能**回显给用户确认**（"我理解成：T30 周二不排课"），不能静默生效。

### 第 1 步：把自由文本升级成"结构化输入 + 规则词典"（方案 1）

前端做约束编辑器；同时保留自由文本，命中词典的自动转结构化。
这一步不需要任何外部服务，能覆盖绝大多数高频需求。

### 第 2 步：加"导入结构化约束"的入口（方案 3 的软件侧）

有了 schema，这个入口就是几十行代码：粘贴 JSON → 校验 → 回显 → 生效。
它使得"外面转好了贴回来"这条路立刻可用，是零风险的试点形态。

### 第 3 步：只在确有必要时，才把模型接进软件（方案 2）

如果确实要做，建议按这个顺序加保险：

1. **实体遮罩**：送模型前，在本地把姓名/班名替换成 ID 或占位符（本地做映射），回传后再还原——
   这样外发的只是"规则骨架"，不含校方数据；
2. **默认关闭**：开关放在设置里，默认不走网络；失败自动回落到规则路径；
3. **schema 校验 + 用户确认**：模型输出不可信，必须校验并让用户点头；
4. **key 管理**：让用户自备，或自建中转服务；不要内置在客户端里；
5. **记录**：把「原话 → 结构化 → 是否被采纳」记成本地日志，既便于排查，
   也便于评估模型在这批语料上的准确率。

### 不建议：本地小模型（SLM）

105 MB 的引擎会膨胀到 GB 级，CPU 推理速度也慢，
与"轻量单文件、双击就用"的产品定位冲突。收益（省掉 API 调用费）远小于代价。

## 8. 风险与边界

| 风险 | 说明 | 缓解 |
|---|---|---|
| 数据外传 | 教师姓名、班级名、校名属校方数据；公网 API 即外传 | 实体遮罩后再送；或走软件外中转 |
| 离线不可用 | 学校网络常见无外网 | 必须保留纯本地的降级路径 |
| 模型幻觉 | 编出不存在的约束、语义漂移 | schema 严格校验 + 用户确认 |
| 客户端密钥 | 桌面程序无法安全保存密钥 | 用户自备 key 或自建中转 |
| 模型升级漂移 | 换版本后输出格式变化、准确率波动 | prompt 与 schema 版本化；保留规则兜底 |
| 语义等价性 | "指定 T30 教 C05" ≠ "T30 的班里至少有一个 C05" | schema 里明确区分，不做隐式推断 |
| 求解变慢 | 约束越复杂，模型越大，25 班已经把时限用满 | 新约束上线前必须跑 25 班基准，盯耗时 |

---

## 9. 待决策的问题

1. **约束能力清单谁写、什么时候写？**（这是所有方案的前置条件，建议最先定）
2. **软件允不允许联网 / 向外发送数据？**（决定方案 2 到底可不可行）
3. **目标用户是"教务室的人"还是"普通老师自助"？**
   （决定方案 3 是长期形态还是只能当试点过渡）
4. **教师分配要不要改成 CP-SAT 决策变量？**
   （一旦改了，B 类大半和 C 类前两条都会自然变得可表达——这可能比接模型更值得先做）
