## 3. 问题一：多解质量不稳定

### 现象

25 个班、5 套方案，两两对比差异如下（每个方案 sheet 共 1375 个有效格）：

| 对比 | 差异格数 | 占比 |
|---|---|---|
| **方案1 vs 方案2** | **2 / 1375** | **0.1%** ← 几乎完全一样 |
| 方案1 vs 方案3 | 682 / 1375 | 49.6% |
| 方案1 vs 方案4 | 661 / 1375 | 48.1% |
| 方案1 vs 方案5 | 650 / 1375 | 47.3% |
| 方案2 vs 方案3 | 682 / 1375 | 49.6% |
| 方案2 vs 方案4 | 662 / 1375 | 48.1% |
| 方案2 vs 方案5 | 651 / 1375 | 47.3% |
| 方案3 vs 方案4 | 418 / 1375 | 30.4% |
| 方案3 vs 方案5 | 446 / 1375 | 32.4% |
| 方案4 vs 方案5 | 424 / 1375 | 30.8% |

**方案1 和方案2 只差 2 个格子。** 25 个班、1375 个格位，只动了 2 格 —— 实质上是同一张课表。

同时，其他方案对之间差异达 30%~50%。**行为不可预测**：有时给两份一样的，有时给两份差很多的。

### 根因

`engine/scheduler/solver/solve.py:126-128`

```python
ones = [bundle.x[k] for k, v in sol.items() if v == 1]
bundle.model.Add(sum(ones) <= len(ones) - 1)
```

这条 no-good 约束的含义是**「下一套方案只要跟这套不完全一样就行」** —— 这是最弱的约束形式。求解器自然选择代价最小的做法：挪一节课交差。

更关键的是：**5 次求解用的是同一个目标函数**（`solve.py:109` 每次都 `solver.Solve(bundle.model)` 同一个 model）。求解器每次都回到同一片最优区域，只在附近微调。

> 至于为何有时差 50%：当所有格位被填满时（自习会自动补齐剩余格位），挪一节课往往触发连锁调换。**这个行为是偶发的，不是设计出来的。**

### 影响

协议 v1.1 明确要求「一次生成 3–8 套**不同**的可行方案」（决策支持模式），项目四条核心需求中的第 2 条也是这个。**当前实现交付的 5 套方案里，部分实质重复，教务处没有真正可选的余地。**

### 解决方案

**核心思路：让每套方案优化不同的目标，而不是同一目标跑 5 遍。**

1. `config.py` 定义 5 组软约束权重档位（均衡型 / 主科优先 / 自习后置 / 教师均衡 / 体育错峰）
2. `model.py` 的 `build_model(problem)` → `build_model(problem, weights=None)`，允许覆盖权重
3. `solve.py` 改为**每个档位单独建模型、各解一次**
4. `solve.py` 增加**汉明距离兜底**：强制新方案与前几套至少差 N 格

```python
def add_hamming_ge(model, x, sols, d):
    """用线性表达式累加差异，不引入辅助变量"""
    for sol in sols:
        terms = [1 - v if sol[k] == 1 else v for k, v in x.items()]
        model.Add(sum(terms) >= d)
```

### 方法可行性验证（独立压测模型）

> ⚠️ **数据来源说明 —— 重要，勿误读**
>
> 下表来自**独立压测模型**（`压测脚本/`），它与本项目引擎是两套东西：
>
> | | 独立压测模型 | 本项目引擎 |
> |---|---|---|
> | 代码 | 压测脚本自建，**不 import 项目任何模块** | `engine/scheduler/solver/` |
> | 数据 | 自建：25 班 / 14 科 / 37 节每周 | `engine/test_input_25/input.xlsx` |
> | 约束 | H1/H2/H5/H6/H8/H12/H14/H15 | H1/H2/H3/H4/H5/H5b |
>
> **它证明了**：差异化权重这个方法方向正确；CP-SAT 在这个问题规模下求解很快。
> **它没有证明**：本项目引擎改完后能达到 86%，也没有测出改后的真实耗时。
> **真实效果必须在引擎里实现修复后、用 `test_input_25` 重跑才能确认。**

| 方法 | 方案间差异 | 每套耗时 |
|---|---|---|
| 现状（naïve no-good） | 2 – 12 变量（**0.01% – 0.09%**） | ~4 秒 |
| **差异化权重** | 1552 – 1656 变量（**约 86%**） | 1.9 – 4.6 秒 |
| 汉明距离约束 | ~1300 变量 | ~13 秒 |

在**该独立模型**上，差异度提升约 150 倍，且速度更快。

> 注：汉明距离阈值实测设 100 / 300 / 600 结果几乎一样（min diff 都是 ~1300），说明天然多样性远超阈值。故汉明约束应作为**下限保护**，设适度值即可（建议总格数的 5% 左右），不要设太高。

## 4. 问题二：评分与命名无区分度

### 现象

25 个班的 `status.json`：

```
方案1 均衡方案      score=100.0  首节主科 80%，自习在下午 100%，教师日均极差 4 节
方案2 主科优先方案  score=100.0  首节主科 80%，自习在下午 100%，教师日均极差 4 节
方案3 自习后置方案  score=100.0  首节主科 80%，自习在下午 100%，教师日均极差 4 节
方案4 教师均衡方案  score=100.0  首节主科 80%，自习在下午 100%，教师日均极差 4 节
方案5 紧凑方案      score=100.0  首节主科 80%，自习在下午 100%，教师日均极差 4 节
```

**评分全是 100.0，描述文字一字不差。**

### 根因（三处）

**① 评分公式永远给不出区分** —— `solve.py:143-144`

```python
score = 100.0 - (pen - min_pen) / span * 30.0
```

其中 `span = max(1.0, max_pen - min_pen)`（`solve.py:139`）。当所有方案惩罚值相同时，`span` 被兜底成 `1.0`、分子为 `0`，于是全部得 100 分。

**② 描述函数只有三个指标** —— `solve.py:42-92`（`_describe`）
只算首节主科占比、自习在下午占比、教师日均极差。方案内容雷同（问题一的后果）→ 三指标必然相同 → 描述必然相同。

**③ 方案名按序号硬贴** —— `solve.py:147`

```python
name=PLAN_NAMES[(i - 1) % len(PLAN_NAMES)],
```

`PLAN_NAMES` 是固定列表（`solve.py:19-22`）。**第 2 套方案永远叫「主科优先方案」，与它是否真的优先主科毫无关系。**

### 影响

> 类比：买手机时五个选项叫「拍照旗舰版」「长续航版」「轻薄版」，点进去参数完全一样、评分全是 5.0 分。

对教务处的实际后果：

1. **无法比较** —— 分数都是 100、描述都一样，凭什么选？
2. **被误导** —— 可能真选「主科优先方案」，以为这套主科排得好，实际未必
3. **说不上哪里不对** —— 界面上有 5 个不同名字的方案，看起来功能是做了的

**错误的标签会导致错误的选择**，比直接说明「只有一套方案」更危险。

### 解决方案

**① 建立与目标函数解耦的统一评价器**（新建 `solver/score.py`）

```python
def evaluate(plan_grid, problem, cfg) -> dict:
    """所有方案用同一把尺子，保证分数可比"""
    return {
        "首节主科率":   ...,   # 越高越好
        "自习下午率":   ...,   # 越高越好
        "教师日均极差": ...,   # 越小越好
        "主科分散度":   ...,   # 同科跨天分布均匀度
        "体育首末节数": ...,   # 越少越好
    }
```

**② 命名改为按实际特征生成**，并用评价器反验：若某方案名不副实，则改名或告警。

**③ `note` 列出该方案最强的两项指标。**

改后目标效果：

```
方案1  均衡型      评分 85.2   各维度均衡，无明显短板
方案2  主科优先型  评分 92.3   首节主科 96%（最高）· 主科分散度 88%
方案3  自习后置型  评分 88.7   自习下午率 100%（最高）· 教师日均极差 3 节
方案4  教师均衡型  评分 90.1   教师日均极差 2 节（最低）· 首节主科 84%
方案5  体育错峰型  评分 83.4   体育首末节 0 次（最低）
```

## 5. 问题一与问题二必须一起修

```
改问题一（每套方案用不同优化目标）
        ↓
各方案「目标值」含义不同 → 现有评分公式（比大小）失效
        ↓
必须同时换成统一评价尺子 = 改问题二
```

- 只改问题一 → 评分逻辑崩掉（拿不同目标的惩罚值互相比较没有意义）
- 只改问题二 → 五套方案内容仍然雷同，评分再准也没有东西可评

**这是本次分析最重要的结论：两者是耦合的。**

## 6. 问题三：无解诊断缺失

### 现象

当约束互相冲突、排不出课时，`engine/engine.py:85-93` 只给出通用提示：

> 约束互相冲突，排不出可行课表。常见原因：固定课与连堂冲突、教师带班过多导致同时段撞课、某班周课时超过可用格数。请检查输入数据或放宽固定课/连堂设置。

教务老师面对 25 个班、20 多位老师、十几条规则，**无法从中得知该改哪一条**，只能反复试错。

### 协议要求

`docs/排课约束目录.md` 的 **G03**：

> 无解时报告最小放宽候选，未经确认不得放宽。

### 解决方案（推荐 deletion filter）

给 `build_model` 增加 `skip` 参数，逐条去掉候选硬约束后重新求解，看是否变可行：

```python
RELAXABLE = ["H4 教师禁排", "H5 固定课", "H6 连堂", "H13 半天制", "H14 日课量"]

def diagnose_infeasible(problem):
    for name in RELAXABLE:
        bundle = build_model(problem, skip=[name])
        if solve_once(bundle) is not None:
            yield name     # 放宽这一条即可求解
```

**代价**：单次求解约 2 秒，试 6 条约 12 秒，完全在 10 分钟预算内。

**关键限制**：`H1/H2/H3/H11` 是**物理约束，永不可放宽**（一位教师不能同时在两间教室、一间教室不能同时容纳两班、一个学生不能同时上两门课），**不得进入候选池**。

**参考实现**：`engine/reference/ly398565721/core/formal_solver.py:144-153` 已有类似做法（把半天制降级为软约束求最小违反集），可移植。

## 8. 验证方法

**基线（改动前）**：本目录 `25班/` 的数据

**验收标准**：

1. 方案两两差异：**最小值不低于总格数的 5%**（当前最低 0.1%）
2. `status.json` 中 5 套方案的**评分不全相同**，且分布合理
3. 方案**名称与实际特征相符**（如「主科优先方案」的首节主科率应明显高于其他方案）
4. 无解场景下，`message` 能**列出具体可放宽的约束名**

**复现命令**：

```bash
cd engine
uv run --with ortools --with openpyxl --with reportlab \
    python engine.py test_input_25 <输出目录> T025
```

对比方案差异的脚本思路：

```python
import openpyxl
wb = openpyxl.load_workbook('result.xlsx')
plans = [s for s in wb.sheetnames if s.startswith('方案')]
def grid(n):
    return {(c.row, c.column): str(c.value)
            for r in wb[n].iter_rows() for c in r if c.value is not None}
gs = [grid(p) for p in plans]
for a in range(len(gs)):
    for b in range(a + 1, len(gs)):
        d = sum(1 for k in gs[a] if gs[a].get(k) != gs[b].get(k))
        print(f'方案{a+1} vs 方案{b+1}: {d} 格不同 ({100*d/len(gs[a]):.1f}%)')
```
